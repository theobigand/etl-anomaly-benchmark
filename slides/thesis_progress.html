02Problemdocs/TD5/PLAN.md

Does machine learning in an ETL pipeline beat plain rules, and for which anomalies?

Industry default is rule-based. Declarative checks in tools such as Great Expectations, Deequ or Soda are auditable and cheap, but they scale poorly with schema complexity, only catch violations the author anticipated, and miss multi-column or distributional anomalies.

Recent work adds ML detectors inside the ETL flow, but the evidence is thin. Published pipelines are mostly conceptual architectures with no reproducible code; when an experiment is reported it is usually one algorithm on one dataset, for instance Isolation Forest on Credit Card Fraud at a near-random ROC-AUC of 0.51.

The stakes are real. Poor data quality is estimated to cost organisations about $12.9M per year, which is why continuous automated checks matter.

This thesis builds the missing head-to-head benchmark of rule-based and classical ML detectors and, as its original contribution, breaks the result down by the kind of anomaly.

Four gaps in the existing benchmarks

  • ADBench, NeurIPS 202230 algorithms on 57 tabular datasets, and PyOD's unified implementations. Both evaluate algorithms in a vacuum, outside any ETL context.
  • declarative rulesThe baselines that dominate production systems are never compared head to head with ML detectors.
  • pipeline integrationNo end-to-end cost: latency, memory, where a detector can sit in the flow.
  • per anomaly typeOne aggregate score per dataset hides that each family catches a different kind of defect.

03Contributionsynthetic.py

A controlled dataset that labels six anomaly types separately

missing valueone or two feature cells set to null. Nulls are the most common real defect.
exact duplicatea clean row copied, same business attributes. A re-ingestion artefact.
univariate outlierone numeric field pushed 15 to 45 times out of range.
multivariate outlierevery field in range, the combination not: an 18-year-old with a 97th-percentile balance and income.
temporal driftrecent-signup rows whose income and balance distribution has shifted up by half.
invalid formatmalformed e-mail, out-of-domain country code, impossible age.

12,360 customer records generated with Faker and NumPy. Income is correlated with balance and transaction size; account age spans three years.

Each type is injected at 3%. Every row carries its anomaly_type, so detection can be measured per category, not only in aggregate.

This is the part existing benchmarks do not provide. It is what the thesis argues for an IMRaD paper rather than a demo paper.

quality/base.py

One interface, one measured path

The demo (make pipeline) and both benchmarks call the same detect() stage. Latency is therefore the real in-pipeline fit + predict + score time, not a lab measurement.

A continuous score() was added on top of the boolean predict() so ROC-AUC and PR-AUC are computable, not only threshold F1. detect(fit_df=...) lets an expensive model fit on a sample and still score the whole stream.

Adding a detector is one subclass and one line in the registry, which the demo and both benchmarks then pick up. The PyOD wrappers use the same path through a small PyODDetector base; the M2 deep models will too.

# every detector, one contract
class Detector(ABC):
    name: str
    def fit(self, df) -> Self: ...
    def predict(self, df) -> Series:   # bool per row
        ...
    def score(self, df) -> Series:     # graded, higher = worse
        return self.predict(df).astype(float)

# classical ML: adapt PyOD, do not reimplement
class PyODDetector(Detector):
    def fit(self, df):
        x = impute(df[self.numeric_cols])
        self.model = self.estimator.fit(scale(x))
        return self

All six subclass one Detector ABC. predict() is the boolean decision used for precision, recall and F1; score() is the graded value used for ROC-AUC and PR-AUC. Deep learning (Autoencoder, LSTM-Autoencoder) is planned for M2 behind the same interface, with reconstruction error as the score.

07Constructionsynthetic.py

How each anomaly type is injected

missing value1–2 of {income, balance, avg amount, tenure, n txn, email, country} → null
duplicateexact copy of a sampled clean row, appended (id included)
univariateone numeric column × U(15, 45)
multivariateage ∈ [18,22] with income and balance at the 97th percentile; or n txn at p97 with avg amount at p3
temporal driftsignup in the last 80 days; income ×1.55, balance ×1.6, avg amount ×1.5
invalid formatemail → malformed; age → {−5, −1, 0, 240, 999}; country → {ZZ, XX, ??, 1}

Base schema. customer_id, age, annual_income, account_balance, n_transactions_30d, avg_transaction_amount, tenure_days, signup_date, email, country.

Five types replace clean rows so the total stays fixed; duplicates are appended, giving ~1.03× the requested row count.

The magnitudes are deliberate design choices and a stated threat to validity. Drift is the subtle one on purpose: the shifted values still fall inside the global range.

No method separates a 0.17% positive class from the tails of normal traffic. Great Expectations is the most selective and wins PR-AUC; Isolation Forest wins ROC-AUC and lifts PR-AUC above both statistical rules but still flags one row in ten.

The best PR-AUC on this dataset, 0.206, still means an analyst reviews about 26 rows to find one fraud. None of these is a production operating point on its own.

Measuring inside the pipeline exposes a cost gap: Great Expectations is about 60× slower than the statistical rules, 13.2s against 0.2 to 0.6s.

LOF and One-Class SVM are absent here. LOF scoring is superlinear in the scored set and OC-SVM training is quadratic, so neither runs at 284k rows in the pipeline. Both are compared on the synthetic set instead, which is itself a pipeline-integration finding.

F1 spans only 0.32 to 0.48 and PR-AUC 0.36 to 0.54, with the random PR-AUC baseline at 0.175. No family is strictly ahead.

Z-score buys perfect precision by firing only on the most extreme rows, at a recall of 0.19. IQR is the opposite trade: the widest net and the best F1.

Among the learned models, Isolation Forest and One-Class SVM lead PR-AUC, but One-Class SVM costs about 20× the time for no quality gain.

The rule-based methods also win ROC against PR here, which is the imbalance trap in miniature even at 17.5% prevalence.

14Findingsdocs/TD5/NOTES.md

What was harder than the plan assumed

  • Great Expectations 1.x is a full API rewriteThe planning notes assumed the 0.18 API. Getting per-row failures out of GX 1.18 needs the COMPLETE result format plus an explicit index column. The flow is ephemeral context, data source, asset, batch, validate. Figured out by running probe scripts against the installed library.
  • One-Class SVM does not scale to pipeline dataTraining is quadratic and Local Outlier Factor scoring is superlinear in the scored set. On the full fraud dataset both are impractical, so the cross-method comparison runs on the controlled dataset, and Isolation Forest on fraud uses a fitted 20k sample.
  • ML detectors are weak on missing valuesImputing before the model removes the signal a not-null rule catches for free: Great Expectations 1.00 on that type against 0.02 to 0.14 for the learned models. The clearest evidence that rules and ML are complementary, not competing.
  • IQR is trigger-happy in high dimensionsOn 30 columns, the rule "flag if any column leaves its fence" fires on 48.6% of Credit Card Fraud rows, which puts its PR-AUC (0.020) barely above the 0.0017 random baseline.
  • Keeping flag and score consistentEach detector derives its boolean and its graded score from one internal computation, so a row can never be flagged with score 0 or scored high without being flagged.
  • Check the installed version before writing library codeNot the version the notes assumed. The GX rewrite alone cost most of a session.

Takeaway

Rules and machine learning are complementary by anomaly type.

The per-type heatmap is what makes that choice actionable, and it is the part existing benchmarks do not provide. The pipeline, the six-type dataset and the per-type benchmark are in place and tested; on aggregate metrics the detector families look interchangeable, per type they are not. Deep learning, a second real dataset, multi-seed runs and a held-out split are the work for M2.
