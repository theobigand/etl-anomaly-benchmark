02Problempaper/main.tex
The question

Does machine learning in an ETL pipeline beat plain rules, and for which anomalies?

The industry default is rule-based. Declarative checks in tools such as Great Expectations are auditable and cheap, but they scale poorly with schema complexity, only catch violations the author anticipated, and miss multi-column or distributional problems.

Recent work adds ML detectors inside the ETL flow, but the evidence is thin: mostly conceptual architectures with no reproducible code, and when an experiment is reported it is one algorithm on one dataset.

This thesis builds the missing head-to-head benchmark and, as its original contribution, breaks the result down by the kind of anomaly.

Four gaps in generic anomaly benchmarks

  • evaluated in a vacuumAlgorithms scored outside any pipeline, no integration cost.
  • no declarative baselineThe rules that dominate production are never in the comparison.
  • one aggregate scorePer dataset, hiding which family is good at what.
  • no operating pointA single flag threshold, not the precision-recall trade-off.

The original contribution

A controlled dataset that labels six anomaly types separately

missing value
one or two feature cells set to null
exact duplicate
a clean row copied, same business attributes
univariate outlier
one numeric field pushed far out of range
multivariate outlier
every field in range, the combination not (an 18-year-old with a top-percentile balance)
temporal drift
recent-signup rows whose income and balance distribution has shifted up
invalid format
malformed e-mail, out-of-domain country code, impossible age

12,360 records generated with Faker and NumPy, six types injected at 3% each, every row tagged with its category. Recall and precision are reported per type.

The injection magnitudes are exposed as one severity multiplier, so the choice of magnitude is swept rather than fixed.

A time-aware drift detector is added for the drift column; it runs on the synthetic dataset only.

The system

One interface, one measured path

The demo and every benchmark call the same detect() stage, so latency is the real in-pipeline fit + predict + score time.

A continuous score() on top of the boolean predict() makes ROC-AUC and PR-AUC computable. detect(fit_df=...) fits on the train slice and scores the test set.

# every detector, one contract
class Detector(ABC):
    name: str
    def fit(self, df) -> Self: ...
    def predict(self, df) -> Series:   # bool per row
        ...
    def score(self, df) -> Series:     # graded score
        return self.predict(df).astype(float)

# classical ML: adapt PyOD, do not reimplement
class PyODDetector(Detector):
    def fit(self, df):
        x = impute(df[self.numeric_cols])
        self.model = self.estimator.fit(scale(x))
        return self

How each anomaly type is injected

Magnitudes are a swept parameter, not a fixed choice

missing value
1–2 of {income, balance, avg amount, tenure, n txn, email, country} → null
duplicate
exact copy of a sampled clean row, id included
univariate
one numeric column × U(15, 45) × severity
multivariate
marginals at the (1 − 0.03/severity) percentile of the clean data
temporal drift
signup in the last 80 days; income × (1 + 0.55·severity), similar for balance and amount
invalid format
email → malformed; age → impossible; country → out of domain

severity = 1.0 is the reference dataset. Missing values, duplicates and invalid formats have no magnitude to scale.

The severity sweep (slide 15) turns "we picked the magnitudes" into a curve and shows the per-type ranking is stable.

The per-type ranking is stable as the magnitudes scale

Univariate outliers are saturated already at severity 0.5. Multivariate outliers show a threshold: Isolation Forest and One-Class SVM climb to 1.0; IQR jumps once the injected percentile crosses its fence.

Temporal drift climbs roughly linearly for the distributional detectors, from ≤ 0.3 at severity 1.0 to 0.6–0.85 at severity 3. The reference drift is simply below every method's floor, not a property of the methods. The same families lead the same columns at every severity.

What was harder than the plan assumed

Findings from the build

  • The operating point matters as much as the algorithmSetting Isolation Forest's contamination to the data prevalence instead of a fixed 10% moves its fraud precision from 0.01 to 0.20 and its multivariate-outlier recall from 0.41 to 0.91. The same estimator, one number changed.
  • Unsupervised detection works in one regimeCardio (rare, outlying): Isolation Forest F1 0.62. Credit Card Fraud (0.17% mixed label): nothing usable. Water Quality (61% majority): everyone at chance. The question is less "rules or ML" than "does this dataset have rare outliers".
  • Great Expectations 1.x is a full API rewriteThe planning notes assumed the 0.18 API. Getting per-row failures out of GX 1.18 needs the COMPLETE result format plus an explicit index column. Figured out by probing the installed library.
  • One-Class SVM does not scale to pipeline dataQuadratic training, and LOF scoring is superlinear in the scored set. On the full fraud dataset only rules and Isolation Forest run.
  • ML detectors are weak on missing valuesImputing before the model removes the signal a not-null rule catches for free: GX recall 1.00 on that type against 0.08 to 0.26 for the learned models.
  • Drift is not a per-row problemOnce diluted by clean recent rows the window mean has moved by about a tenth of a standard deviation. The dedicated detector scores 0 at the reference severity; the severity sweep shows it needs a several-times-larger shift.

Takeaway

Rules and machine learning are complementary by anomaly type.

The per-type heatmap is what makes that choice actionable. Across three real datasets, unsupervised detection pays off only on Cardio, where the anomalies are genuinely rare outliers. The pipeline, the four datasets, the held-out protocol, the curves and the CI are in place and tested. Deep learning and the write-up are the work for M2.
